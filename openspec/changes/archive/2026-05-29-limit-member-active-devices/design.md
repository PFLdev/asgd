## Context

当前项目已有会员相关能力，但语义集中在“教育设备激活会员”和“教育会员权益领取”：

- `member_activation_record` 记录设备是否完成会员激活，一台设备只能激活一次。
- `edu_benefit_receive_record` 记录教育权益领取结果，依赖设备白名单、分布式锁和数据库唯一键防重复领取。

这些能力都不是“账号当前有多少台设备正在使用会员功能”。本变更需要新增一层会员功能准入控制：账号可以继续登录多台设备，但只有最多 3 台设备能在同一时间访问会员功能。

## Goals / Non-Goals

**Goals:**

- 在服务端统一限制同一账号最多 3 台设备同时使用会员功能。
- 使用 Redis 作为实时活跃设备租约存储，通过原子操作保证并发请求下不会突破 3 台限制。
- 对已占用名额的设备刷新租约，对崩溃、断网或未主动退出的设备通过 TTL 自动释放。
- 提供清晰的超限响应，便于客户端提示用户当前账号已有 3 台设备正在使用会员功能。
- 保留关键事件审计能力，为后续设备管理页、踢出设备、风控分析预留空间。

**Non-Goals:**

- 不限制账号登录设备总数。
- 不实现完整登录体系、Token 签发或设备指纹 SDK。
- 不在第一阶段实现用户手动管理设备列表或远程踢出指定设备。
- 不改变现有会员激活、教育权益领取的核心业务规则。

## Decisions

1. 使用 Redis ZSET 表示账号的活跃会员设备集合。

   - Key：`member:active_devices:{userId}`
   - Member：`deviceIdHash`
   - Score：最近一次成功使用会员功能的时间戳。
   - 设备详情可使用 `member:active_device:{userId}:{deviceIdHash}` 保存 `sessionId`、`leaseUntil`、`lastSeenAt`、客户端信息等。

   原因：该限制是实时、高频、短生命周期状态，Redis 比 MySQL 更适合作为主判断路径。

   备选方案：使用 MySQL 租约表并通过行锁控制。该方案审计和恢复能力更强，但每次会员功能调用都会增加数据库压力，并发锁粒度也更重。

2. 使用 Lua 脚本或等价原子操作完成“清理过期、判断数量、占用/续租”。

   单次准入判断应在 Redis 内原子完成：

   ```text
   1. 移除 score 小于过期阈值的设备
   2. 如果当前 deviceIdHash 已存在，刷新 score 和详情，返回 ALLOWED
   3. 如果集合大小小于 3，加入当前设备，返回 ALLOWED
   4. 否则返回 LIMIT_EXCEEDED，并可返回当前活跃设备摘要
   ```

   原因：如果使用 `count -> add` 的非原子流程，并发第 4、5 台设备可能同时通过。

   备选方案：使用现有 `EduBenefitDistributedLockService` 风格的分布式锁。该方式可行，但会引入额外锁生命周期问题；Lua 单 Key 原子脚本更直接。

3. 默认策略为“第 4 台设备拒绝”，不自动挤掉已有设备。

   原因：拒绝策略最稳定、最容易解释，也不会让正在使用会员功能的设备突然失效。返回信息应能让客户端提示用户稍后再试或前往设备管理。

   备选方案：自动挤掉最久未活跃设备。该方案能提升新设备进入成功率，但被挤掉设备体验不可预期，且需要额外通知机制。

4. 租约依赖 TTL 自动释放，并由会员功能请求刷新。

   推荐第一阶段租约窗口为 5 到 15 分钟，具体值通过配置管理。普通会员 API 每次请求刷新租约；长时间使用场景可由客户端 heartbeat 刷新，但服务端仍必须在实际会员功能入口二次校验。

   原因：客户端 release 不可靠，崩溃、断网、杀进程都可能导致占用无法主动释放。

5. 审计走异步或轻量记录，不阻塞主准入路径。

   关键事件包括 `ACQUIRED`、`REFRESHED`、`REJECTED_LIMIT_EXCEEDED`、`EXPIRED`、`RELEASED`、`REDIS_UNAVAILABLE`。第一阶段可以先落应用日志或新增审计表，后续再接 MQ。

   原因：准入判断在会员功能请求链路上，审计失败不能让核心请求大面积变慢。

## Risks / Trade-offs

- [Risk] Redis 不可用导致无法判断活跃设备数 → Mitigation：配置降级策略。默认建议短时 fail-open 并记录告警，避免会员功能大面积不可用；如业务强约束版权，可配置 fail-closed。
- [Risk] 客户端伪造或频繁变化 `deviceId` → Mitigation：服务端对 `deviceId` 做 hash 存储，并结合认证上下文、`sessionId`、设备注册信息或风控校验；不要只信任裸请求体字段。
- [Risk] 部分会员功能入口未接入准入校验 → Mitigation：优先做统一拦截器、注解或 Service 门面，并在测试中覆盖核心会员入口。
- [Risk] 租约 TTL 过短会误释放正在使用的设备 → Mitigation：TTL 配置化，并根据会员功能形态设置 heartbeat 或请求刷新频率。
- [Risk] 租约 TTL 过长会让异常退出设备长时间占用名额 → Mitigation：初始值保守设置，监控超限拒绝和续租间隔后再调优。
- [Risk] Redis 与审计表状态不一致 → Mitigation：实时准入以 Redis 为准，审计只用于排查和后续管理；不要在第一阶段用审计表反向参与实时判断。
- [Risk] 多应用实例并发访问同一账号 → Mitigation：所有实例使用同一 Redis Key 和同一 Lua 脚本，确保账号维度原子性。

## Migration Plan

1. 新增配置项控制会员活跃设备限制开关、最大设备数、租约 TTL、Redis 异常降级策略。
2. 新增 Redis 准入服务并在非生产环境验证 Lua 脚本的并发行为。
3. 将核心会员功能入口接入准入校验，先以配置开关灰度启用。
4. 增加监控和日志，观察拒绝率、Redis 异常、平均活跃设备数。
5. 灰度稳定后默认启用。

回滚策略：关闭配置开关，会员功能不再执行设备数限制；保留审计数据不影响现有业务。

## Open Questions

- 会员功能入口的最终边界需要确认：哪些 API 必须受限制，哪些仅查询或非会员能力不受限制。
- `deviceId` 的来源和可信度需要确认：来自登录设备注册、客户端上报，还是现有业务请求字段。
- Redis 不可用时最终采用 fail-open 还是 fail-closed，需要产品和业务风险一起确认。
- 是否需要第一阶段就返回当前 3 台活跃设备的摘要，还是仅返回超限状态和提示。
